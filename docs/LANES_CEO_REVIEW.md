## Landscape check (web search; Aside not installed)

- Layer 1 (tried and true): site screening in GIS by consultants; pro formas in Excel; permitting through expediters
  and land-use attorneys.
- Layer 2 (what the market says): AI site-ID tools are multiplying for LIHTC rentals and builders: Parcell (LIHTC site
  scoring), Prophetic (D.R. Horton land analysis), TestFit and Deepblocks (massing). AI in affordable finance is mostly
  auditing pro formas and drafting (Novogradac). Permitting speed is being attacked by law, not software: AB 253's
  30-day shot clock with third-party reviewers, SB 4 by-right approval.
- Layer 3 (first principles): for a homeownership nonprofit, "where" and "does it pencil" are one decision. A site is
  only worth pursuing if the families who would live there can keep the home and the gap can be closed. No tool in the
  landscape prices a site through the families' sustainable mortgages. **Eureka logged.**

## 0A. Premise challenge

- Real problem: Habitat OC needs 100 homes; the lab wants one lane solved convincingly, shown by a user running a
  sample scenario.
- Keystone already answers two lanes directly (Find it, Fund it) and one barely (Clear it).
- Do-nothing cost: pitching "all three lanes" contradicts "pick one" and dilutes the story; the current demo is a
  self-playing film, which fails the new "user runs a scenario" rule outright.
- Proxy risk: the 3D demo shows capability, not a decision a user makes. The lab's lanes are questions a staff member
  asks; the demo must show that person getting an answer.

## Review Sections (strategy-only depth)

### Section 1: Architecture

```
                          Mac app (WebKit, pywebview)        browser (make serve)
                                     \                          /
                                      v                        v
   NEW  Sign-in + sessions ---> FastAPI app (keystone/app/server.py) <--- existing auth: /mcp + missions token/loopback
                                      |
   NEW  Scenario service --------+----+-----------------------------+
   (30 households, parcel,       |                                  |
    assumptions, provenance)     v                                  v
                         existing tools.py (15 tools)        NEW document generator (templates
                          |       |        |                  + optional Claude prose, figures locked)
                          v       v        v
          sites/site_score  sustainability  capital  + NEW household aggregation
                                  |
                          homekeeper + NEW entry point for given households
                                  |
                    agents/runtime.py (Claude or scripted) over MCP (stdio)
                                  |
                       sandbox/runner.py (seatbelt / bwrap)
```

Data flow, four paths for the new scenario flow:
- Happy: seed loads, 7 steps render from precomputed results; edits recompute only touched households.
- Nil: a household field missing in a saved scenario: refused on load, the scenario opens read-only with the field named.
- Empty: a scenario with zero households: Steps 2-7 show "add households" and nothing computes.
- Error: optimizer or simulation raises: the step shows the error with the failing household named; downstream steps
  stay on the last good result, marked stale.

State machine (scenario): `seeded → editing → computing(preview) → computed(full) → saved`; `computing → error`;
`reset` returns to `seeded` from any state. Invalid: `preview → saved` or `preview → documents` (blocked, round 2).

Findings:
- WARNING: the scenario service is a new coupling point between UI, tools and documents; it must call tools.py, not
  reimplement models (taste reference: one implementation, many doors).
- WARNING: single point of failure: the local state dir; a corrupt scenario file must not stop sign-in.
- OK: rollback is the previous .dmg (v0.1.0) and git revert; no migrations.
- Value test: no process artifacts are added; documents (P4/S4) are product output for staff.

### Section 2: Error & Rescue Map (capabilities)

```
  CAPABILITY               | WHAT CAN GO WRONG                     | FAILURE CLASS
  -------------------------|---------------------------------------|----------------------
  Sign-in                  | wrong password, corrupt account store | auth failure / storage error
  Scenario load/save       | corrupt or old-format file            | validation error
  Household recompute      | invalid input, model exception, slow  | ValidationError / model error / timeout
  Capital aggregation      | a household with no feasible design   | domain result (meets_target false)
  Agent run (Step 5)       | Claude error, refusal, malformed tool | API error / refusal / bad JSON
  Document generation      | figure mismatch after Claude prose    | integrity check failure
  PDF / download           | WebKit print fails, download blocked  | platform error
  Map tiles                | offline                               | network error

  FAILURE CLASS            | RESCUED? | RESCUE ACTION                         | USER SEES
  -------------------------|----------|---------------------------------------|------------------------------
  auth failure             | Y        | refuse, no field disclosure           | "Wrong email or password"
  storage error            | Y ← must prove | open with seed, keep bad file aside | banner naming the file
  validation error         | Y        | field-level refusal (tools.py bounds)  | field named, nothing recomputes
  model error              | Y ← must prove | household marked failed, rest stays | household-level error
  meets_target false       | Y        | show most sustainable design, flagged  | "no design reaches 95%"
  Claude API error/refusal | Y ← must prove | fall back to scripted for the run    | "running offline policy" label
  bad JSON from a tool     | Y        | call_tool maps is_error to {"error"}   | agent sees error, trace shows it
  integrity check failure  | Y ← must prove | discard Claude prose, use template   | template version + note
  platform error (PDF)     | Y ← must prove | offer Markdown download instead      | "PDF unavailable, Markdown saved"
  network error (tiles)    | Y        | blank map background (existing)        | blank background
```

GAPS: none silent by design; five rows are "must prove" conditions for the implementer.

### Section 4: Data flow & interaction edge cases

```
 INPUT (edit) -> VALIDATE (tools.py bounds) -> RECOMPUTE (touched households) -> PERSIST (scenario) -> RENDER
   nil/wrong type -> refused, field named          timeout -> preview kept, labelled        conflict -> last write wins, recorded with who/when
   too long/big   -> refused                        exception -> household failed, rest kept stale -> marked stale until full result
```

| Interaction | Edge case | Handled? | How |
|---|---|---|---|
| Next during a recompute | double advance | must prove | Next disabled until the step's result is full or preview-labelled |
| Edit twice fast | stale submit | must prove | latest edit wins; earlier computation discarded |
| Reset mid-agent-run | orphaned run | must prove | reset cancels the run; trace marked cancelled |
| Sign-out mid-scenario | unsaved edits | must prove | autosave the scenario before sign-out |
| Two roles edit at once (same Mac) | conflict | yes | shared scenario, edits recorded (round 3) |
| Back button / Go menu | lose place | must prove | step index persisted per scenario |

### Section 7: Performance

- Slowest paths: full-cohort recompute (30 × ~1.6 s ≈ 48 s at 1,500 paths) → precomputed seed, touched-household
  recompute, preview at reduced paths; Step 5 with Claude (streams); PDF render.
- Memory: 30 households × record=True arrays (120 × n_paths) is small (< 50 MB at 2,000 paths).
- Caching: seed results cached with the scenario; recompute keyed by household inputs.

### Section 8: Observability

- Per scenario step: timing and outcome logged to the run trace (existing trace.jsonl pattern), so a failed demo can be
  replayed.
- /healthz already reports the sandbox; add scenario-store health (must prove).
- Joy to operate: a "demo readiness" check in the Mac app (sandbox ok, seed present, offline path ok) before going on stage.

### Section 9: Deployment & rollout

- Ship as v0.2.0 through the existing desktop workflow (tag → CI build + smoke → private release → publish_public.sh).
- No migrations. Feature flag: the scenario page can ship behind a menu item until its e2e passes.
- Rollback: the v0.1.0 .dmg stays on the public release page.
- Post-deploy: desktop smoke extended to run the full scenario offline.

### Section 10: Long-term trajectory

- Debt: three new entry points (aggregation, homekeeper for households, provenance) need docs; reversibility 4/5.
- Platform potential: the scenario model becomes the unit of work for real affiliates (replace synthetic households with
  an affiliate's applicants; calibrate on their loan outcomes).
- Phase 2: real applicant import + affiliate outcome data; Phase 3: multi-affiliate cloud with real accounts.

                  |                                         ^  (Next/Back, arrows, Go menu, reset from anywhere)

| Agent run | streaming toasts | - | "offline policy" label | graded brief | cancelled trace |

Information hierarchy per step: the answer (one number or decision) first, then the evidence, then the differentiator
